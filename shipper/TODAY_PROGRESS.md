## Second batch

- Booking creation, status reads and cancellation require a shipper session; records are scoped to the authenticated owner.
- Booking retries use stable UUIDs and insert-only writes with request fingerprints. Reusing an ID for another owner or different load returns 409.
- Truck identity, capacity and fare are validated/computed on the server; customer name comes from the account.
- Open loads are claimed with a conditional atomic database update. Captain identity comes from the session; supplied identity, ratings and verification badges are ignored.
- Trip updates require the assigned captain and a permitted transition, with a conditional update to reject stale changes.
- Shipper cancellation persists and is rejected after pickup. Sample loads are no longer offered as actionable jobs.
- Captain trip history and active-trip recovery now read owned database records.
- Booking/acceptance/status mutations wait for API success. Errors display instead of silently succeeding. Matching and tracking no longer fabricate progress after timeouts/outages.
- Backend regression suite: 35 passing tests, with persistence stubs and local HTTP checks. Real MongoDB races and browser end-to-end testing remain outstanding.

## 26 October 2026 — Shipment handover verification

- Replaced predictable booking-ID-derived codes and format-only verification with random six-digit pickup/delivery challenges generated by the API for the owning shipper at the appropriate trip stage.
- Challenges expire after ten minutes, allow five attempts, store only a keyed hash, and are consumed with the successful transition. Wrong-owner requests, stale codes, expired codes and concurrent replay cannot complete a handover. Cancellation removes any challenge.
- Shipper tracking now offers code generation with expiry and regeneration feedback. Codes are only kept in screen memory and are never included in captain/booking read responses. There is a 30-second regeneration cooldown and a single-process issuance rate limiter.
- Captain handover controls accept six digits, prevent duplicate submissions and await API success. Failed verification preserves the input for correction. Cancellation awaits server success and is hidden after pickup.
- Validation: 52 backend tests passed (17 new handover tests); both frontend type checks and production builds passed. Tests use synthetic persistence and local HTTP requests; real MongoDB concurrency and browser end-to-end checks remain outstanding.
- Deploy the API and both frontends together because the old four-digit handover flow is no longer accepted. Production login still needs an SMS provider. No changes from this batch have been committed or pushed.

Next priorities: restore shipper bookings after refresh, enforce one active trip per captain atomically, replace demo vehicle/KYC and earnings data, harden sessions, review remaining dependency advisories, and complete real database/browser validation.

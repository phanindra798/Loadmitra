1The pitch

30-second version

"LoadMitra is a freight marketplace for India, like Uber but for trucks. Shippers book a truck and see a transparent per-tonne price, and truck drivers, called Captains, accept loads that match their vehicle. It supports full loads, shared loads for small shippers, and discounted return loads so trucks don't drive back empty. I built it as two React portals backed by one Node/Express/MongoDB API, with phone-OTP login, an atomic booking-acceptance flow, OTP-verified pickup and delivery, live updates over Server-Sent Events, and I deployed it on AWS EC2 behind nginx with HTTPS and CloudWatch monitoring."

2-minute version (structure it like this)

  1. Problem (20 s): Indian road freight is fragmented. Small businesses can't fill a whole truck, prices are negotiated by phone, and many trucks return empty after a delivery.
  2. Solution (20 s): Two apps. The Shipper portal does search → quote → book → track. The Captain portal does go online → accept → pickup → deliver → earnings. Three booking modes: full, shared, return.
  3. Architecture (30 s): Two TanStack Start (React + SSR) frontends and one shared Express + TypeScript API on MongoDB. The bookings collection is the bridge between the two portals.
  4. Hard parts (30 s): Two captains accepting the same load at once is solved with conditional atomic updates. A captain holding two active trips is blocked by a partial unique index. A captain faking a delivery is blocked by a shipper-issued handover OTP. Clients can't tamper with prices because the server recomputes distance and fare. Live updates use SSE with a polling fallback.
  5. Delivery (20 s): Deployed on one AWS EC2 instance: nginx reverse proxy, PM2 process manager, Let's Encrypt HTTPS, MongoDB Atlas, CloudWatch logs and metrics, and an IAM role for S3. There are 104 automated backend tests plus browser end-to-end tests.
Interviewers love a story with a problem → a decision → a trade-off → a result. For every technology below there's a "why" and an "alternative considered". Use them.

Why the name

"Mitra" means friend in Hindi/Sanskrit. A "friend for your load" is a friendly, India-first brand. Supporting 6 Indian languages (English, Hindi, Telugu, Tamil, Kannada, Malayalam) follows from the same thinking: many drivers are more comfortable in their regional language.

Why a marketplace with two separate apps

  • Shippers and drivers have different goals, devices and screens. Mixing them in one app makes both worse.
  • The proven model is ride-hailing (Uber/Rapido): a customer app plus a driver app. LoadMitra applies it to goods.
  • One shared backend keeps a single source of truth for each booking that both sides watch.
Interviewers often ask "How did you get this idea?". Answer with a real personal story, because they can tell when it's made up. A useful template:
"I noticed [what you saw: a family business, a relative who transports goods, the trucks you see near markets or highways, a news article about empty return trips]. When I looked into it, I learned that [a fact: small shippers overpay, trucks return empty, prices aren't transparent]. Ride-hailing solved a similar matching problem for people, so I wanted to build that for goods, with features specific to India like shared and return loads and regional languages."

6Tech stack: frontend

Each card answers four interview questions: What is it? Why this one? How is it used in LoadMitra? What else could you have used?

React 19

WhatA JavaScript library for building UIs out of reusable components (functions that return UI). State changes re-render only what changed.
WhyIndustry standard, huge ecosystem (Radix, TanStack), component reuse across two portals, and strong hiring relevance.
How usedEvery screen and widget is a component. It uses hooks (useState, useEffect, useReducer, useContext, useSyncExternalStore) and Context providers for app state (BookingProvider, CaptainProvider).
AlternativesVue, Angular, Svelte. React was chosen for its ecosystem and familiarity.

TypeScript

WhatJavaScript with static types. The compiler catches mistakes like passing a string where a number is expected before the code runs.
WhyThe domain has many shapes (Booking, Trip, Payout, PriceBreakdown). Types keep the server, shipper and captain consistent and make refactoring safe.
How usedThe whole repo, all three apps. Shared domain types live in server/src/types/index.ts and are mirrored in features/*/types.ts.
AlternativesPlain JavaScript with JSDoc. That's riskier as the project grows.

TanStack Start (SSR framework)

WhatA full-stack React framework. Pages are server-side rendered (the HTML is built on the server) and then hydrated (made interactive) in the browser.
WhyA faster first paint on slow mobile networks, good SEO for the landing page, and type-safe routing out of the box. Cookies let SSR read the language and theme with no flash.
How usedsrc/router.tsx, src/start.ts (error middleware), src/server.ts (SSR wrapper that shows a friendly error page). Built with Nitro: the node-server preset for AWS (.output/server/index.mjs run by PM2), or vercel.
AlternativesNext.js (most popular), Remix, a plain Vite SPA. TanStack was chosen for end-to-end type safety and close integration with TanStack Router/Query. The project was also scaffolded with Lovable, which uses this stack.

TanStack Router (file-based routing)

WhatA type-safe router. The file name decides the URL: app.track.$id.tsx → /app/track/:id.
WhyRoute params and search params are typed (e.g. validateSearch on the matching page), and nested layouts with <Outlet/> keep providers mounted.
How used__root.tsx is the HTML shell; app.tsx is the layout with sidebar, bottom nav and providers. routeTree.gen.ts is auto-generated.
AlternativesReact Router.

TanStack Query (React Query)

WhatA library that manages server state: fetching, caching, loading/error states, background refetch, polling and cache invalidation.
WhyThe captain app shows several server resources that must stay fresh (trips, offers, earnings, profile). Doing that by hand with useEffect is error-prone.
How usedcaptain-context.tsx defines queries with polling intervals (trips 3 s/30 s, offers 6 s/30 s, earnings 15 s/60 s; the faster value is used when the live stream is down). Live events call invalidateQueries. The shipper quote screen uses it for the server estimate with the local estimate as initialData.
AlternativesSWR, Redux Toolkit Query, plain fetch.

Vite

WhatA build tool and dev server: instant start, hot module replacement, optimized production bundles.
WhyMuch faster than Webpack. TanStack Start runs on it.
How usedvite.config.ts pins ports (8080/8081) with strictPort and selects the Nitro preset. VITE_* env vars (API URL, portal URLs) are baked in at build time.

Tailwind CSS 4

WhatUtility-first CSS: style with small classes like px-4 rounded-xl text-sm directly in the markup.
WhyFast and consistent styling with a small CSS output. Design tokens (CSS variables) make light/dark themes easy.
How usedstyles.css defines colour tokens; use-theme.ts toggles the dark class on <html>. Responsive classes (lg:) give a sidebar on desktop and a bottom tab bar on mobile.
AlternativesCSS Modules, styled-components, MUI.

Radix UI + shadcn/ui

WhatRadix provides unstyled, accessible primitives (dialog, dropdown, tabs…). shadcn/ui is a set of pre-styled copies of them that live in your own repo (components/ui/).
WhyKeyboard and screen-reader support for free, and full control because the code is ours, not a black-box dependency.
How usedDialogs, sheets, the OTP input (input-otp), toasts (sonner), icons (lucide-react).

Other frontend pieces

i18nA custom lightweight t() function (features/*/i18n.tsx) with 6 languages and an English fallback. No heavy library is needed.
MapMapCanvas is a CSS/SVG visual placeholder, so no Google Maps key or cost. Real tiles can be added behind the same overlay.
GeolocationBrowser GPS plus a free key-less reverse geocoder (BigDataCloud), falling back to coordinates.
Storagelib/storage.ts: cookie first (so SSR can read it), mirrored to localStorage. Cookies are marked Secure over HTTPS.
QualityESLint + Prettier; frontend unit tests with Node's built-in test runner.

7Tech stack: backend

Node.js (v22 in production)

WhatA JavaScript runtime for servers. It's event-driven and non-blocking, so one process handles many concurrent connections.
WhyOne language across the stack, and very good at I/O-heavy work (database calls, many open SSE connections). Runs on Arm (t4g) with no changes.
AlternativesJava/Spring Boot, Python/FastAPI, Go.

Express 4 (4.22.3)

WhatA minimal web framework: routing plus a middleware chain (functions that run in order for each request).
WhySimple, battle-tested, enormous ecosystem (helmet, cors, cookie-parser, morgan).
How usedapp.ts builds the app (it's separate from index.ts so tests can import it). asyncHandler is needed because Express 4 doesn't catch rejected promises. The central errorHandler returns clean 400/500 responses.
AlternativesFastify (faster), NestJS (more structure), Koa.

Zod

WhatRuntime schema validation. TypeScript types disappear at runtime; Zod actually checks incoming JSON.
WhyAll client input is untrusted. You get clear 400 errors and typed data after parsing.
How usedEvery controller (e.g. createBookingSchema, Indian phone regex ^[6-9]\d{9}$, vehicle number normalization). Also environment variables in config/env.ts: the server refuses to boot with bad config (fail fast).

JWT (jsonwebtoken) + phone OTP

WhatA JWT is a signed token containing {userId, role, jti, exp}. The OTP is a 6-digit one-time code that proves you own the phone.
WhyOTP: Indian users expect phone login, not passwords. JWT: stateless verification, so no session lookup per request (except a revocation check).
How usedHS256 with the algorithm pinned, 30-day expiry, a unique jti per login for logout revocation. Sent as Authorization: Bearer and as an httpOnly cookie (SameSite=None; Secure in production).
AlternativesServer-side sessions (Redis), Firebase Auth, Auth0/Cognito.

Server-Sent Events (SSE)

WhatA one-way, long-lived HTTP response through which the server pushes text messages to the browser.
Why not WebSockets?Updates only flow server → client, SSE is plain HTTP (works through nginx and proxies, auto-reconnect semantics), and it needs no extra library. Client → server actions remain normal REST calls.
How usedGET /api/events, see §16.

8Tech stack: database (MongoDB)

MongoDB + Mongoose, hosted on MongoDB Atlas

WhatMongoDB is a document database that stores JSON-like documents in collections. Mongoose adds schemas, validation and models in Node. Atlas is MongoDB's managed cloud service.
WhyA booking is naturally a nested document (pickup, drop, captain snapshot, price snapshot, handover OTP). Reading one document gives the whole booking with no joins. Single-document updates are atomic, which is the basis of the race-condition fixes. Atlas M0 is free and managed (no DB server to run on the 1 GB EC2).
How used4 collections; indexes for uniqueness, TTL expiry and the partial "one active trip" rule; findOneAndUpdate with conditions; one aggregation pipeline ($facet, $group, $dateToString with timezone) for earnings.
AlternativesPostgreSQL (relational, transactions, strong for reporting). A fair answer: "Postgres would also work. I chose MongoDB because bookings are document-shaped and single-document atomic updates covered my concurrency needs. If I needed complex cross-entity reporting or multi-table transactions, I'd consider Postgres."

9Tech stack: AWS and DevOps

The deployment kit lives in deploy/aws-ec2/. Every piece is explained here: what it is, why it's used, and how to talk about it.

Amazon EC2 (t4g.micro, Amazon Linux 2023, Arm/Graviton)

WhatA virtual machine in the AWS cloud. t4g.micro = 2 vCPU (burstable), 1 GB RAM, on AWS Graviton (Arm) processors.
WhyThe cheapest way to run 3 Node processes plus nginx 24/7. Graviton is cheaper than x86 t3.micro for the same size. Node is plain JavaScript, so Arm needs no code changes. Amazon Linux 2023 is AWS-optimized and ships the CloudWatch agent package.
DetailsRegion ap-southeast-2 (Sydney), because the free-plan account is pinned to one region. 12 GB gp3 disk. A 2 GB swap file (setup-ec2.sh) because 1 GB RAM is tight for three Node processes.
AlternativesElastic Beanstalk, ECS Fargate, App Runner, Lambda, Lightsail. All are more managed but cost more or don't fit SSE/long connections well.

Elastic IP

WhatA static public IPv4 address that you attach to the instance.
WhyThe IP survives stop/start, so DNS names (sslip.io), the Atlas IP allow-list and TLS certificates stay valid. Note: an unattached Elastic IP is billed, so release it if you delete the instance.

Security Group (virtual firewall)

RulesSSH 22 from my IP only; HTTP 80 and HTTPS 443 from anywhere. Ports 4000/8080/8081 are not open: the Node apps bind to 127.0.0.1 and only nginx is public.
WhyLeast exposure. Only the reverse proxy is reachable from the internet.

nginx (reverse proxy + TLS termination)

WhatA high-performance web server used here as a reverse proxy: it receives public traffic and forwards it to local apps by hostname.
WhyOne public entry point for 3 apps (virtual hosts by server_name), HTTPS termination, HTTP→HTTPS redirect, and protection of Node from direct exposure.
Key configA special location /api/events with proxy_buffering off and proxy_read_timeout 1h so SSE messages pass instantly and the stream isn't cut between 25-second pings. X-Forwarded-For $remote_addr overwrites the header (clients can't spoof their IP). client_max_body_size 1m matches the API limit. WebSocket upgrade headers on the portals (Vite/HMR compatibility).

Let's Encrypt + certbot + sslip.io

WhatLet's Encrypt issues free TLS certificates; certbot requests them and edits the nginx config. sslip.io is a free DNS service where api.13-233-10-20.sslip.io resolves to 13.233.10.20.
WhyHTTPS with no domain purchase. HTTPS is required for Secure cookies, geolocation in browsers, and trust.
RenewalCertificates last 90 days. A cron job runs certbot renew twice a day and reloads nginx.

PM2 (process manager)

WhatA production process manager for Node: it starts, restarts on crash, and starts again on reboot.
How usedecosystem.config.cjs declares 3 apps: loadmitra-api (dist/index.js), loadmitra-shipper and loadmitra-captain (Nitro .output/server/index.mjs). max_memory_restart (300M/250M) keeps the 1 GB box stable. kill_timeout: 10000 gives the API's graceful shutdown (8 s) time to drain. pm2 startup systemd restarts after reboot. pm2-logrotate: 10 MB × 7 files, compressed.
Alternativessystemd units, Docker + docker-compose.

IAM role (instance profile)

WhatAn identity attached to the EC2 instance that grants it AWS permissions through temporary credentials. No access keys are stored anywhere.
PoliciesAWS-managed CloudWatchAgentServerPolicy plus an inline policy allowing only s3:PutObject/GetObject/DeleteObject on loadmitra-documents-…/*. That's least privilege.

Amazon S3

WhatObject storage for files.
SetupA private bucket (Block Public Access ON), SSE-S3 encryption, in the same region. It's prepared for future captain KYC document uploads; the app doesn't upload anything yet. Say this honestly.

Amazon CloudWatch (agent, logs, metrics, alarms)

LogsThe agent ships PM2 logs and the nginx error log to log groups /loadmitra/api, /shipper, /captain, /nginx, kept for 14 days.
MetricsCustom namespace LoadMitra: mem_used_percent, disk used_percent, swap_used_percent every 5 minutes. EC2 doesn't report memory by default; that's why the agent is needed.
AlarmsStatusCheckFailed ≥ 1 and mem_used_percent > 90 → SNS email.
Health/health returns 200 {db:"up"} or 503 {status:"degraded", db:"down"} so monitoring sees a DB outage.

Cost controls (AWS Budgets)

A zero-spend budget alert is created first. The kit avoids billed extras: no second instance, no load balancer, no NAT gateway, no idle Elastic IP. The README estimates about USD 12–13/month, covered by new-account credits.

{ dialCode, phone, role, codeHash /* HMAC, never the code */, attempts (≤5), expiresAt /* TTL */ }

Booking: the bridge between the two portals

{ bookingId: "LM-<UUID>", shipperId, requestFingerprint, customerName,
  mode: "full"|"shared"|"return", pickup:{label,address,city}, drop:{...},
  distanceKm /* server-computed */, truckTypeId, truckTypeName, loadWeightKg, goodsType,
  agreedPrice /* server-computed */, priceSnapshot /* frozen breakdown */,
  status:     "open" → "accepted" | "cancelled"            // marketplace state
  tripStatus: accepted → enroute_pickup → at_pickup → picked
              → enroute_drop → delivered | cancelled      // driving state
  acceptedByCaptainId, captain /* snapshot */, handoverOtp:{stage,codeHash,expiresAt,issuedAt,attempts},
  completedAt, payoutSnapshot /* frozen at delivery */, createdAt, updatedAt }

RevokedToken

{ jti, expiresAt /* TTL: removed when the JWT would have expired anyway */ }
"I separated status (is the load still on the market?) from tripStatus (where is the truck?). And I store snapshots of the price, the captain and the payout, so history and earnings don't change if the rate card or the captain's vehicle changes later. That's the same idea as storing the price on an order line instead of looking it up from the product table."

Trip state machine

 accepted ─► enroute_pickup ─► at_pickup ─[pickup OTP]─► picked ─► enroute_drop ─[drop OTP]─► delivered
    │              │               │
    └──────────────┴───────────────┴──────────► cancelled   (only before goods are on the truck)

Defined in trips.controller.ts as a transitions map. No skipping, no going backwards, no cancelling after pickup.

15Hard problems solved

These are the parts that impress interviewers most. Practise explaining each as problem → naive approach → why it fails → my solution.

1. Two captains accept the same load at the same time

Naive: read the booking, check status === "open", then save. Fails: both read "open" before either writes, so both accept (a race condition). Solution: one conditional atomic write:

Booking.findOneAndUpdate(
  { bookingId, status: "open", truckTypeId: myTruck, loadWeightKg: { $lte: capacity } },
  { $set: { status: "accepted", acceptedByCaptainId: me, captain: snapshot } })

MongoDB applies a single-document update atomically, so only one filter can still match. The loser gets null → 409.

2. One captain must not hold two active trips

Naive: "count active trips, then accept": the same race from two tabs or two servers. Solution: a partial unique index on acceptedByCaptainId that only covers active bookings. The database itself rejects a second active trip (error 11000 → 409 ACTIVE_TRIP_EXISTS). When the trip ends, the booking leaves the index's filter automatically. The API refuses to accept at all (503) unless the index is confirmed installed.

3. A double-tap or retry creates duplicate bookings

Solution: idempotency. The client generates bookingId once per draft, and the server does $setOnInsert keyed on bookingId + shipperId + fingerprint (a SHA-256 of the load details). A retry returns the same booking; the same ID with different details or a different owner → 409. A retry can never re-open or re-price an accepted booking.

4. Stale updates (old tab, slow response)

Every trip transition includes the current tripStatus in its filter (optimistic concurrency). On the client, mergeBookings/latestTrip never move a record backwards (newest updatedAt wins, else the later stage).

5. Proving pickup and delivery really happened

The shipper generates a handover code for the current stage. The captain must enter it. Verification takes three atomic steps: reserve an attempt → constant-time hash compare → transition only if the same challenge is still present. That stops brute force, replay and regeneration races.

6. Account switching leaks data

useSessionKey() turns the token into a React key. A login, logout or account change (even in another tab, via the storage event) remounts the whole state tree and query cache, so account A's data is never shown to account B.

7. Timezone-correct earnings

Servers run in UTC, but captains think in IST. The aggregation groups with $dateToString using timezone: "Asia/Kolkata", and week/month windows are computed in IST. Legacy trips without completion data are counted separately rather than guessed.

8. Zero-downtime-ish restarts

On SIGINT/SIGTERM the API closes SSE streams, stops accepting connections, finishes in-flight requests, disconnects MongoDB, and exits (with an 8 s cap). PM2's kill_timeout is 10 s.

9. Starting even when the DB is unreachable

HTTP starts immediately; MongoDB connects in the background with retry every 10 s. /health reports 503 until the DB is up, and deploy.sh waits for it.

16Live updates (Server-Sent Events)

Server: services/live-events.service.ts

  • Signals, not data: events are only {"type":"booking","id":"LM-…"}, {"type":"trip",…} or {"type":"offers"}. Clients re-fetch through normal owner-checked endpoints, so the stream can never leak data.
  • publishBookingChange notifies the shipper, the assigned captain, and (if the job board changed) every connected captain.
  • Limits: 5 streams per user, 2,000 per server, 64 KB write buffer (slow clients are dropped), streams end at token expiry or after 1 hour, a heartbeat : ping every 25 s, and X-Accel-Buffering: no for nginx.

Client: lib/live.ts, lib/use-live-events.ts

  • Uses fetch streaming instead of EventSource, because EventSource can't send an Authorization header.
  • Exponential backoff with jitter on reconnect: 1, 2, 4… up to 30 s, ±25%.
  • After a reconnect it emits a local resync to reload everything (messages may have been missed).
  • The stream closes when the tab is hidden or the page is left, because browsers allow ~6 HTTP/1.1 connections per host and idle streams would block API calls. The browser test found this bug.
  • Polling stays as a slow fallback (30–60 s while live, 3–15 s when disconnected).
"I chose SSE over WebSockets because updates only flow from server to client. Actions are normal REST calls. SSE is plain HTTP, so it works through nginx with buffering turned off, and it's simpler to secure. I made the events carry only IDs, so authorization stays in one place: the regular API."

21How to scale it

  1. Move shared state out of memory: rate limits → Redis (ElastiCache); SSE fan-out → Redis pub/sub so any instance can notify any client.
  2. Run several API instances behind an Application Load Balancer across 2+ AZs, in an Auto Scaling group (or containerize with Docker and run on ECS Fargate). Raise ALB idle timeout for SSE.
  3. Serve portals separately: Vercel or CloudFront + Lambda/ECS for SSR; static assets on CloudFront CDN.
  4. Database: Atlas M10+ with backups, replica set and read preference; indexes are already designed for owner-scoped queries.
  5. CI/CD: GitHub Actions → test → build image → push to ECR → deploy; infrastructure as code (Terraform/CDK).
  6. Observability: structured JSON logs (pino), request IDs, metrics/tracing (CloudWatch, X-Ray or OpenTelemetry).
  7. Security: WAF on the ALB, Secrets Manager, SSM Session Manager, domain + ACM certificates.
"The design already pushes correctness into MongoDB with atomic updates and unique indexes, so it stays correct with many API instances. The only in-process pieces are the rate limiter and the SSE registry, and both are marked in the code to move to Redis when scaling horizontally."

22Interview questions and model answers

Answer in your own words. These are model answers, not scripts to memorize.

A. Project and product

Tell me about your project.
Use the 30-second pitch (§1), then offer: "Should I go deeper into the architecture, the concurrency problems, or the AWS deployment?"
How did you get the idea?
Use your own true story (see the "Make it yours" box in §2), then the three problems: empty return trips, small shippers overpaying, opaque prices.
Who are the users and what problem does each have?
Shippers want a reliable truck at a fair, transparent price. Captains want more paid trips and fewer empty kilometres. One platform with three modes serves both.
What makes it different from existing apps?
India-first: shared and return loads as first-class modes, a per-tonne price range (how traders think), 6 regional languages, and OTP-verified handover at pickup and drop for trust.
What was your role?
Describe honestly what you designed, built, tested and deployed. If you used AI tools or a scaffold (the frontends were scaffolded with Lovable), say so and explain what you reviewed, fixed and hardened yourself; the commit history shows the auth, booking and concurrency fixes.
What would you do differently?
Start with server-authoritative flows and tests from day one (the early version trusted client prices and accepted any OTP), plan for Redis earlier, add CI/CD, and pick Postgres or Mongo deliberately after modelling reporting needs.

B. Architecture

Why two frontends and one backend?
Different users and devices, independent deploys and simpler apps; one API and database keep a single source of truth for each booking, which both sides watch.
Monolith or microservices? Why?
A modular monolith. One domain, small team, and atomic single-database operations. Microservices would add network calls and distributed transactions without benefit at this size. The layered structure makes later extraction possible.
Explain the request flow in your backend.
helmet/cors/json/cookies → route → rate limit → requireAuth (JWT + revocation) → requireRole → controller (Zod validation) → service (business logic) → model (Mongoose) → response; errors go through asyncHandler → errorHandler.
How do the two portals communicate?
They never talk directly. Both read and write the same booking through the API; SSE signals tell each side when to re-read.
Why is app.ts separate from index.ts?
So tests can build the Express app without listening on a port or connecting to a database.

C. Frontend

Why React? Why TanStack Start instead of Next.js?
React for its ecosystem. TanStack Start for SSR plus fully type-safe routing and tight integration with TanStack Query. Next.js would be a valid alternative.
What is SSR and hydration? Any problems you hit?
The server sends ready HTML; React then attaches event handlers. Browser-only APIs (localStorage, window) must run in useEffect; otherwise server and client markup differ (hydration mismatch). I keep the session key stable during the first hydration so the tree doesn't remount and drop clicks.
How do you manage state?
Server state with TanStack Query (captain) or a Context + useReducer store with merge logic (shipper); UI and draft state in React state/context; preferences in cookies. No Redux needed.
What is TanStack Query doing for you?
Caching, deduplication, loading/error states, polling (refetchInterval), cancellation via AbortSignal, and invalidation when a live event arrives.
How do you handle logout or switching accounts safely?
The token becomes a React key; any change remounts the provider tree and clears the query cache. Cross-tab changes come through the storage event.
How is multi-language support done?
A small t(key, vars) with per-language dictionaries, falling back to English then the key; the choice is persisted in a cookie so SSR renders the right language.
How do you show a price instantly if the API is slow?
The same formula runs locally as initialData; the server estimate replaces it. The booking itself always uses the server's computation.

D. Backend and API

Why Express? Why Zod?
Express is simple and has a mature middleware ecosystem. Zod validates untrusted input at runtime (TypeScript types vanish at runtime) and also validates env vars at boot.
How do you handle errors in async routes?
Express 4 doesn't forward rejected promises, so asyncHandler catches them and calls next(err); a central handler returns 400 for bad JSON and a generic 500 otherwise, without leaking stack traces.
What's the difference between 401 and 403? Why 404 for someone else's booking?
401 = we don't know who you are; 403 = we know you but you aren't allowed. For other people's records we return 404 so we don't reveal that the ID exists.
How does pagination work?
Cursor-based: ?before=<lastId>, sorted by _id descending, fetching limit+1 to know if there's a next page. It's stable when new bookings arrive, unlike page numbers.
What is idempotency and where do you use it?
Repeating a request has the same effect as doing it once. Booking creation uses a client-generated ID plus a fingerprint and $setOnInsert, so network retries don't duplicate or alter bookings.
How does your rate limiter work, and its limitation?
A fixed window per key in a Map: OTP routes keyed by IP+phone, signed-in routes by account (many Indian mobile users share carrier IPs). It returns 429 with Retry-After. The limitation: it's per-process, so multiple instances need Redis.
What does TRUST_PROXY do?
Behind nginx every request comes from 127.0.0.1. Setting Express trust proxy to 1 makes req.ip the real client from X-Forwarded-For, and nginx overwrites that header so clients can't spoof it.
How does graceful shutdown work?
On SIGTERM/SIGINT: close SSE streams, server.close() to finish in-flight requests, disconnect Mongo, exit; force exit after 8 s. PM2 waits 10 s.

E. Database

Why MongoDB instead of SQL?
Bookings are nested documents read as a whole; atomic single-document updates cover the concurrency needs; Atlas has a free managed tier. Postgres would also work and would be better for complex reporting or multi-entity transactions.
What indexes did you create and why?
Unique identity (dialCode, phone, role); TTL for OTPs and revoked tokens; unique bookingId; the partial unique active-trip index; compound indexes for owner-scoped history and earnings (see §8).
What is a partial index?
An index that only includes documents matching a filter. Here, uniqueness applies only to active trips, so a captain can have many completed trips but only one active one.
What is a TTL index?
MongoDB deletes documents automatically after a date field passes. It's used for expired OTP challenges and revoked tokens.
Did you use transactions?
No. Every critical change touches one document, and MongoDB guarantees single-document atomicity. Conditional filters plus unique indexes give the needed guarantees without multi-document transactions.
How are earnings calculated?
One aggregation: match the captain's delivered trips → sort → $facet into per-day totals (grouped in IST), the 20 latest ledger rows, and a count of legacy trips without completion data.
How did you migrate identity to include the country code safely?
Back-fill dialCode="+91", create the new unique index, then drop the old one. Uniqueness holds at every moment, and it's idempotent, so it runs on every boot.

F. Security

Walk me through your login flow.
send-otp: validate phone → random 6-digit code → store its HMAC with a 5-minute TTL and 0 attempts. verify-otp: atomically increment attempts on an unexpired challenge (<5) → compare hashes → register if new → atomically delete the challenge → sign a JWT (with jti) → httpOnly cookie + token in the body.
Why hash OTPs? Why HMAC rather than plain SHA-256?
If the DB leaks, codes can't be read. A 6-digit code has only a million possibilities, so a plain hash is trivially brute-forced; an HMAC needs the server secret.
JWTs are stateless. How does logout work?
Each token has a unique jti. Logout stores it in a revoked list with a TTL equal to the token's expiry; requireAuth checks it and fails closed (503) if the DB is unavailable. Live streams for that session are closed.
How do you stop a client from paying less?
The server ignores the client's price and distance, recomputes both from the catalogue and cities, validates truck capacity, and stores an immutable price snapshot.
How do you prevent IDOR (accessing others' data)?
Every query includes the owner ID taken from the verified token (shipperId or acceptedByCaptainId), never from the request body.
What's timingSafeEqual and why use it?
A comparison that takes the same time whether the values match early or late, so attackers can't learn a correct hash byte by byte from response timings.
What security weaknesses remain?
The demo OTP mode in the AWS deployment, the token copy in a JS-readable cookie (XSS), no KYC verification, in-memory limits. Each has a planned fix (§19, §20).
What does helmet / CORS protect against?
helmet: clickjacking, MIME sniffing and missing HSTS, via headers. CORS: browsers on other websites can't call the API with the user's credentials; only the two portal origins are allowed.

G. Concurrency and real-time

Two captains tap Accept at the same millisecond. What happens?
Both send findOneAndUpdate({status:"open", …}). MongoDB applies them one at a time; the first flips it to accepted; the second's filter no longer matches → null → 409 "unavailable".
How do you guarantee one active trip per captain across servers?
A partial unique index in the database: the DB rejects the second active trip with a duplicate-key error, which becomes 409. It doesn't depend on application memory.
Why SSE and not WebSockets or polling only?
Updates are one-way, SSE is plain HTTP and proxy-friendly, and it needs no extra library. Polling alone is either slow or wasteful, so polling is kept only as a fallback.
Why not use the browser's EventSource?
It can't set an Authorization header. I use fetch streaming with my own parser, backoff and resync.
What happens if the SSE connection drops?
The client reconnects with exponential backoff and jitter, then triggers a resync to refetch everything; meanwhile polling speeds up to 3–15 s.
Describe a tricky bug you found.
The browser end-to-end test showed that after a few navigations every API call hung. Chrome kept previous pages' SSE streams open, using up the ~6 HTTP/1.1 connections per host. The fix: close the stream on pagehide and when the tab is hidden, reopen with a resync. A test now asserts exactly one stream is open.

H. AWS and DevOps

Explain your deployment architecture.
Use the "How to say it" box in §18.
Why EC2 and not Lambda, Beanstalk or ECS?
Cost (one small instance inside the credits), long-lived SSE connections (a poor fit for Lambda), full control and learning value. ECS Fargate + ALB would be the next step for scaling.
Why t4g (Graviton/Arm)?
It's cheaper than t3 at the same size and Node runs unchanged on Arm. (On a legacy free-tier account t3.micro would be the free option.)
What is a reverse proxy and why nginx?
A server in front of your apps that receives public traffic and forwards it. nginx gives one public entry for three apps by hostname, TLS termination, redirects, and SSE-specific settings, and keeps Node off the public internet.
How does HTTPS work in your setup? How are certificates renewed?
certbot obtains Let's Encrypt certificates for the three sslip.io hostnames and configures nginx with an HTTP→HTTPS redirect; cron runs certbot renew twice a day and reloads nginx.
What is sslip.io?
A free wildcard DNS: a hostname that contains the IP resolves to that IP. You get valid HTTPS without buying a domain.
Why PM2?
It keeps the three Node apps alive, restarts on crash or memory overuse, restarts on reboot through systemd, reloads on deploy, and rotates logs.
Why an IAM role instead of access keys?
The instance gets short-lived credentials automatically, so there are no long-lived keys to leak or rotate, and permissions are least-privilege (CloudWatch agent plus specific S3 object actions).
What do you monitor and how?
The CloudWatch agent ships PM2 and nginx logs (14-day retention) and memory, disk and swap metrics; alarms on instance status checks and memory >90% go to SNS email; /health reports DB connectivity.
Why add swap, and why build locally?
1 GB RAM is tight for three Node processes; swap absorbs spikes. Building React/TypeScript needs more memory than the box has, so builds run locally and only the compiled output is shipped.
How do you handle secrets?
They live only in .env on the instance (chmod 600), never in git; the DB password is written through a hidden prompt; JWT_SECRET comes from openssl rand -hex 32; AWS access is through the role. Next step: SSM Parameter Store / Secrets Manager.
How would you make deployments safer?
Versioned release folders with symlink switch and rollback, a CI pipeline running tests first, health-check gating, and eventually blue/green behind a load balancer.
How much does it cost?
About USD 12–13/month (t4g.micro, public IPv4, 12 GB gp3), covered by new-account credits; Atlas M0 is free. A zero-spend budget alert guards against surprises.
Why is MongoDB in the same region as EC2?
Every request makes several DB round trips; cross-region latency (100+ ms each) would make the app slow.

I. Testing and quality

How did you test it?
104 backend regression tests with stubbed persistence, integration tests on a temporary real MongoDB for race conditions and indexes, browser end-to-end tests driving Chrome through the DevTools Protocol, and frontend unit tests, all with Node's built-in test runner.
Why not Jest?
node:test is built in, fast and needs no extra dependencies; it covered every need.
How do you test a race condition?
Against a real MongoDB in the integration suite: fire concurrent accepts and assert exactly one succeeds and the active-trip index rejects the others.

J. Behavioural and scaling

How would you scale to 1 lakh (100,000) users?
§21: Redis for rate limits and SSE pub/sub, multiple API instances behind an ALB in an Auto Scaling group or ECS, CDN for portals, Atlas M10+ with backups, CI/CD and observability.
What was the hardest part?
Pick one from §15, e.g. guaranteeing one active trip per captain under concurrency, and tell it as problem → naive approach → why it fails → database-enforced solution → test.
What did you learn?
Never trust the client; push invariants into the database; design for failure (fail closed, retries, fallbacks); real browsers reveal bugs unit tests can't; and deployment and operations are part of the product.
If you had one more month?
Real SMS and maps, KYC uploads to S3, payments via UPI, CI/CD, and Redis for horizontal scaling.
